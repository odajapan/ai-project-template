# /review — code-review + 日本語の説明

組み込みの `/code-review` をユーザーが直接実行すると、結果（英語の JSON）が表示されて
終わり、Claude が説明を足すターンが無い。このコマンドは `code-review` スキルを
**Claude から** `Skill` ツールで呼び、レビューが出力した直後に日本語の説明を続ける。

## 手順

1. `Skill` ツールで `code-review` を呼ぶ。`args` には受け取った引数（`$ARGUMENTS`）を
   そのまま渡す。対象・深さ・`--fix` / `--comment` の意味は `/code-review` と同じ。
   `ultra`（クラウド実行で結果が同期で返らない）と `--post` は扱わない。渡されたら
   「`/code-review <args>` を直接実行してください」と案内して終わる。
2. スキルの出力はスキルの契約に従う（インラインで読み込まれた場合は Claude 自身が
   レビュアーとして JSON を出す、または `ReportFindings` で報告する。フォーク実行なら
   結果が返る）。**その出力を二重に貼り直さない。** ただし、ユーザーの画面に findings が
   まだ出ていない場合（フォーク実行の結果がツール結果としてしか届いていない時）は、
   JSON ブロックを一度だけそのまま貼ってから説明に進む。
3. 続けて日本語の説明を書く。**番号はスキルの出力順に固定**（並べ替えない。重要度は
   「見立て」で示す）。findings が空なら「指摘なし」と、レビュアーが確認した点を 2〜3 行で。

   ```
   N. **<ファイル名> <行>: <問題を一文で>**
      起きうること: <failure_scenario の要約。どの入力・状態で、何が壊れるか>
      直し方: <summary / failure_scenario に書かれた修正案。無ければ自分の案と明記>
      見立て: 本物のバグ / 設計判断 / 整理（軽微） + 一言
   ```

   `category` / `verdict` が付いている時の対応: `verdict=CONFIRMED` と `correctness`
   系の category は原則「本物のバグ」、`PLAUSIBLE` は「設計判断」寄り、
   `simplification` / `efficiency` / `test-coverage` は「整理」。迷ったら根拠を一言添える。

4. 最後に **番号で** 「直すべき」「任意」「対応不要（理由）」に振り分け、直すなら提案する
   ブランチ名（`claude/<task>`）を 1 行添える。既にマージ済み / 別 PR で対応済みの指摘は
   その旨を書く。
5. 説明は簡潔に（CLAUDE.md の文体ルールに従う。1 指摘 3〜4 行）。コードは書かない。
   レビュー対象が自分の直前の変更なら、同意できない指摘は根拠を付けてそう書く。

## やらないこと

- `--fix` が無い限りファイルを変更しない（`--fix` 付きの変更はスキルに任せる）。
- findings の内容を省略・言い換えしない（日本語説明は **追加**であって置き換えではない）。
- PR へのコメント投稿は `--comment` が付いた時だけ（スキルに任せる）。
